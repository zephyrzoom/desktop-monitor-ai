## ci: 每次构建的产物自动发布到 Release

- 需求：GitHub Actions 每次执行生成的 artifacts 都自动发布到 Release。用户确认策略：
  按分支固定预发布（rolling，覆盖同名文件）+ 所有运行含 PR。
- `.github/workflows/build.yml`：把 `release-nightly` 换成 `release-continuous`，去掉
  main/master 分支限制；分支 push / workflow_dispatch → tag `continuous-<branch>`，
  PR → `continuous-pr-<n>`；`v*` tag 仍走原来的 `release` job 发正式版。
- 用 `overwrite_files: true` 覆盖同名安装包，下载链接长期不变；job 级 `concurrency`
  按分支/PR 串行发布，避免并发运行互相覆盖；fork PR 的 GITHUB_TOKEN 只读，跳过发布
  （Actions artifacts 仍照常上传）。
- 旧的 `nightly` Release 不再更新，可在 GitHub 页面手动删除。
- 验证：YAML 解析通过、`npm run typecheck` 通过。

## 调研：能否用 Rust GPUI 重写 UI 层（仅评估，未改代码）

- 结论：**技术上全部功能都能实现**，且本项目后端已是 Rust-first，迁移条件好于一般 Tauri 应用；
  但 5500 行前端 + 1871 行 CSS 零复用须重写，GPUI 仍 pre-1.0，当前不建议整体迁移。
- 分层判断：
  - 可原样复用：`src-tauri/src/{db,analyzer,monitors,config,logger,paths}/`（≈4000 行，纯逻辑 + 跨平台 crate）；
    仅需把 `runtime.rs` 里的 Tauri `AppHandle`/`Emitter` 抽象成事件总线，19 个 command 退化成直接函数调用。
  - 必须重写：全部 React 页面/组件/CSS、HashRouter、CSP、`navigator.clipboard` 兜底、Vite `define` 版本号注入。
  - 需换实现/外挂：托盘（NSStatusItem）、开机自启（LaunchAgent）、单实例、Dock 恢复、打包签名/自动更新、权限预检。
    官方 GPUI 不含这些；`gpui-ce` / `adabraka-gpui` / `fc-gpui` 等 fork 或 `tray-icon` crate 可补。
- 生态现状（2026-11）：crates.io 官方 `gpui` 停在 0.2.2，实际活跃的是 `gpui-pre` 0.3.x 周快照与
  `gpui-ce` / fork，API 常有 breaking change；`gpui-component`（longbridge，已更名 GPUI Kit）有 75+ 组件
  （DatePicker/Select/Progress/Chart/Table/Sidebar/Theme/Image/Markdown 等），覆盖本项目全部 UI 形态；
  GPUI 原生支持 IME 合成（中文输入）、剪贴板、`reveal_path`、文件对话框、系统暗色主题。
- 渐进路径：`tauri-plugin-gpui`（0.1.0，2026-10 发布，需 `tauri 2.12+` + `features=["unstable"]`）可让
  GPUI 窗口与 WebView 窗口在同一进程共存，适合逐页替换；缺点是两个不稳定栈叠加。
- 收益：去掉 WKWebView/WebView2 与 JS 桥、免 WebView2 依赖、内存/启动更轻；代价：整条 CI 打包/签名链路重建、
  Linux wgpu/X11/Wayland 门槛、组件库版本 pin 带来的维护成本。

## 调研：性能优化入手点（仅评估，未改代码）

- **实测基线**（只读查 `~/Library/Application Support/desktop-monitor/monitor.db`）：
  screenshots 130 行 / active_windows 286 行 / daily_analysis 0 / periodic_summary 0 / task_memory 0，
  磁盘 36 张 jpg（20M），monitor.db 140K，数据目录共 35M（其中约 14M 是 WKWebView 的
  Cache/Code Cache/GPUCache），dist-renderer 316K（gzip 94K），release 二进制 7.3M。
  **当前数据规模极小，DB 全表扫不是瓶颈**，索引类优化属于预防性。
- 已验证：`EXPLAIN QUERY PLAN SELECT * FROM screenshots WHERE date(timestamp,'localtime')=...` → `SCAN screenshots`；
  改成裸 timestamp 半开区间 → `SEARCH ... USING INDEX idx_screenshots_timestamp`。根因是对列套函数使索引失效。
- **第一梯队（低风险，优先）**：
  1. `analyzer/mod.rs:199-252 prepare_images()`：磁盘已是 1280 宽 q80 JPEG，却 `image::open` →
     `to_rgb8()`（整图 clone）→ `JpegEncoder` 重新编码；`width > MAX_IMAGE_WIDTH` 分支对本项目数据永不命中。
     改为 `fs::read` + base64，历史大图才走慢路径（约 15~25 行）。
  2. `analyzer/llm.rs:189 chat()` 每次新建 `reqwest::Client`（连接池/TLS session 全丢），放到 `Runtime` 复用。
  3. `analyzer/mod.rs:1092 Scheduler`：60s 相对 sleep + `%H:%M` 字符串相等判定，漂移会跳过目标分钟
     → **当天日报可能不生成，是正确性 bug 而非性能问题，最该先修**。改 `interval_at` 或绝对 `sleep_until`。
  4. 过度取数：`commands.rs:98` 为 `.len()` 拉回当天全部窗口行（可由 app_usage.count 求和）；
     `data_daily_analysis('all')` / `getPeriodicSummary(...,'all')` 拉全部 result_json 只为渲染日期 pill。
  5. 前端 `AnalysisContext.tsx:122` value 未 memo + `analysis:result` 按天广播 → 30 天补算约 300 次重复 invoke；
     4 个页面每次渲染都 `JSON.parse(result_json)`。
- **第二梯队**：`capture()` / `get_active_window()` / `prepare_images` 等同步 FFI 与 IO 跑在 Tokio worker 上，
  应包 `spawn_blocking`；`start_all()`→`cleanup()` 同步跑在 `setup()` 主线程导致首屏白屏，应后台化；
  6 处相对 sleep 改 `interval`；`analysis_running` 全局锁覆盖整条 30 天补算链，期间手动分析全返回 busy。
- **第三梯队（暂缓）**：生成列 `local_date` + 复合索引 / `prepare_cached` / `synchronous=NORMAL` /
  单 `Mutex<Connection>` 拆读写池（WAL 并发读被浪费）；`reqwest` 默认 feature 裁成 rustls + `panic="abort"`；
  **去掉 WebView 才是常驻内存最大单点，但等于重写 UI**。
- **明确不要动**：`FilterType::Triangle`（image 里第二快）、`Shared` 的 SeqCst 原子、prompt 里的 format!、
  StrictMode、事件订阅（无泄漏）、auto_vacuum（磁盘体积非查询速度）、前端产物拆包。
- 建议先加计时打点（`capture` / `prepare_images` / `chat` / `setup` 首尾 `Instant`），跑一天看真实分布再定顺序。
