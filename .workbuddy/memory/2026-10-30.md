# 2026-10-30

## 定时日报时间仍从 0 点开始 —— 根因排查

用户反馈：每天定时生成的日报，记录时间段仍然错，从 0 点左右开始。

查到四个叠加因素：

1. **线上跑的是旧二进制**：`src-tauri/target/debug/desktop-monitor` 时间戳 10-28 14:38，
   早于 10-29 的时区修复，所以 `hhmm()` 读到的仍是 UTC。
2. **prompt 没给每张截图的时间**：图片是批量发的，模型只看到「时间范围: X-Y」，
   不知道每张图的时刻，只能自己编时段。
3. **`parse_timestamp` 完全失效**：它用 `parse_from_rfc3339` 解析库里
   `2026-06-04T08:38:41.474`（无时区后缀）→ 必然失败 → `unwrap_or(0)`，
   于是所有时间戳变 0，`create_batches` 的 gap 判断永不触发，
   整天截图被合并成一个超大批次，模型只能按总范围编时间。
4. **定时任务选了日期**：`run_scheduled` 用 `today`。若 schedule 在凌晨触发，
   分析的是一天刚开始（只有 0 点后几张截图）；而且日报一旦写入就不会被
   backfill 重算（它只补"缺失"日期），于是每天留一条错误日报。

## 修复内容

- `analyzer::parse_timestamp` 改用 `parse_db_timestamp()`（naive 解析后按 UTC → Local）。
- `prepare_images` 返回 `(原始下标, base64)`，用于对齐时间戳；
  `build_daily_analysis_prompt` 新增 `screenshot_times`，prompt 里输出
  「本次截图时间点（共 N 张，与图片顺序一一对应）」，并明确要求 time_range 落在此范围。
- 新增 `scheduled_target_date()`：06:00 前触发总结「昨天」，否则总结「今天」；
  `backfill_range` 的区间终点同步改成 target，避免凌晨生成当天的空日报。
- 新增 `analysis_reanalyze_recent(days)` 命令 + 日报页「重算最近 7 天」按钮，
  用于修正历史上已生成但内容错误的日报（今天不重算）。
- 重新 `cargo build` 出新的 debug 二进制。

## 经验

- 本机数据在 `~/Library/Application Support/desktop-monitor/monitor.db`，
  但 find/mdfind 显示只有到 6 月的数据；排查时先确认「用户跑的是哪份产物」，
  别只改代码就以为生效（`target/debug` 的时间戳是最快的证据）。
- SQLite 的 `strftime('%Y-%m-%dT%H:%M:%f','now')` 产出**不带时区后缀**的 UTC 字符串，
  chrono 里必须用 `NaiveDateTime` 解析再 `from_naive_utc_and_offset`。
